# 内网智能体产品需求与交付方案

> 文档状态：需求基线，待确认后实施
>
> 本文面向 Ubuntu 24.04 服务端、Windows 10/11 客户端的内网部署。
> `BRAND_NAME`、`REAL_SERVER` 和 Logo 素材均为部署时注入的私有配置，不写入公开仓库。

## 1. 建设目标

基于现有 PicoAide Harness，交付一套名称为 `BRAND_NAME` 的内网智能体平台。实际名称由私有渠道配置注入。平台可以在无 HTTPS、无外网依赖的内网环境运行，让管理员集中管理用户、模型、Key、Skill、审计和客户端更新，让普通用户通过 Windows 客户端直接使用内网大模型。

首要目标是可用性和兼容性：服务端能够稳定接入多种 OpenAI 兼容模型，客户端能够完成登录、对话、流式响应和更新，管理员能够清楚查看用户 Prompt 与模型 Response。

## 2. 部署与网络

### 2.1 HTTP-only 模式

- 服务端、管理端、客户端 API、模型网关、更新清单和安装包统一支持 HTTP。
- 部署不要求购买或配置 HTTPS 证书。
- 服务端监听内网地址，示例使用 `REAL_SERVER:8080`。
- 客户端首次启动时填写服务端地址，验证成功后持久化保存，后续启动不再重复填写。
- 生产部署使用固定内网 IP 或内网 DNS，避免 WSL 动态地址导致客户端失联。
- 管理端提供当前服务端地址、健康状态和版本信息。
- 文档明确说明 HTTP 会明文传输账号、密码、Token 和模型内容，这是内网部署的明确取舍。

### 2.2 服务端交付

- 提供 Ubuntu 24.04 可执行文件。
- 提供 PostgreSQL 初始化、迁移和备份说明。
- 提供 systemd 服务文件。
- 提供首次安装、升级、回滚和卸载脚本。
- 提供配置模板，人工需要填写的内容尽量收敛到服务端地址、数据库、模型端点和 Key。
- 提供启动后的 `/healthz`、`/readyz` 检查方法。

### 2.3 Windows 客户端交付

- 只提供 Windows 10/11 x64 安装包，不支持 Windows 32 位。
- Windows 安装包不做代码签名，内网用户按部署说明安装。
- 安装后可自动读取服务端地址。
- 首次启动没有服务端地址时显示简短配置向导。
- 客户端能够从登录的服务端获取更新，不依赖 GitHub 或外网更新服务器。

## 3. 品牌和视觉定制

### 3.1 品牌配置

- 产品显示名统一使用私有渠道配置中的 `BRAND_NAME`。公开仓库继续使用占位符，实际名称在私有渠道配置中注入。
- Logo、窗口图标、任务栏图标、托盘图标、安装包图标、登录页 Logo、管理端 Logo 和 favicon 均从同一套品牌素材派生。
- 不在业务代码中硬编码品牌名，支持通过渠道配置替换。
- 管理端、客户端和帮助文档中删除不必要的“企业”字样。
- “企业版”角标改为私有渠道配置的自定义角标文案。

### 3.2 Logo 素材

- Logo 和 SVG 视觉方案由大模型根据产品定位生成，先产出候选设计，再选定最终方案。
- 使用选定的 SVG 作为几何源，生成 PNG、ICO、安装包图标、托盘图标和网页 favicon。
- Logo 由产品方直接生成并选定，不要求用户额外提供设计文件。
- 提供浅色和深色背景下的可读版本。
- 统一检查尺寸、透明边距、Windows 图标多尺寸和 Electron 打包兼容性。
- 交付包中附带品牌替换说明，后续只替换素材和渠道配置即可重新生成全部图标。

## 4. 客户端界面

### 4.1 左侧导航

- 移除“更多”入口。
- 将定时任务、能力中心、连接器、浏览器、应用中心和设置直接展示。
- 入口与设置在同一层级排列。
- 缩小入口宽度和左右内边距。
- 缩短入口之间的垂直间距。
- 减少左侧栏空白，使对话区域获得更多宽度。
- 确保中文长文案、窗口缩放和 Windows 10 常见分辨率下不重叠、不截断。

### 4.2 Token 用量

- 管理端和客户端不展示金额、余额、充值、付费或计费文案。
- 所有相关区域改为显示输入 Token、输出 Token、总 Token、今日用量和月度用量。
- 保留后端原始 usage 数据兼容字段，避免已有接口和历史数据损坏。
- 没有 usage 数据时显示明确的“暂无用量”，不能显示误导性的金额或空白卡片。

## 5. LLM 网关兼容

### 5.1 供应商和模型

服务端支持配置多个 OpenAI 兼容端点，包括 DeepSeek、GLM、千问、MiniMax、腾讯混元以及其他兼容服务。

每个端点包含：

- Base URL
- API 兼容类型
- 一个或多个 API Key
- 默认模型
- 超时和重试策略
- 是否启用 Responses API
- 是否启用 Chat Completions

### 5.2 模型发现

- 管理员填写 Base URL 和 Key 后可以一键获取 `/models`。
- 模型列表显示模型 ID、供应商、能力和更新时间。
- 支持手动隐藏不需要的模型。
- 客户端只显示服务端允许使用的模型。
- 模型发现失败时显示可诊断错误，不覆盖已有配置。

### 5.3 API 适配

- 同时支持 Chat Completions 和 Responses。
- 支持流式和非流式响应。
- 统一处理 SSE 事件、结束事件、错误事件和 usage。
- 兼容不同供应商的 reasoning、tool call、system message 和多模态字段差异。
- 对上游没有实现的字段进行能力降级，不因单个可选字段导致整次请求失败。
- 保留原始上游错误，向客户端返回用户可读的错误说明。

### 5.4 多 Key 轮询

- 一个供应商可以配置多个 Key。
- 默认采用轮询策略。
- 429、限流、超时、连接失败和可重试 5xx 触发 Key 冷却并切换下一个 Key。
- 401、403 等不可恢复错误将 Key 标记为异常并在管理端提示。
- 冷却时间结束后自动恢复尝试。
- 同一请求最多执行有限次数的 Key 切换，避免重复生成和无限重试。
- 所有已启用 Key 使用全局轮询策略，不按模型拆分轮询池。
- 管理端显示 Key 的启用状态、最近错误、冷却截止时间和成功率，不显示完整 Key。

## 6. Prompt/Response 审计

### 6.1 审计范围

审计页面默认只显示用户与模型的交互记录：

- 用户 Prompt
- 模型 Response
- 用户、会话、工作区
- 模型和供应商
- 请求时间和耗时
- 输入、输出和总 Token
- 流式或非流式状态
- 请求失败原因

登录、登出、普通管理操作、后台任务、健康检查、Key 切换等内容不再混入 Prompt/Response 审计列表。若系统仍需保留合规日志，应放在独立的系统操作日志页面，不影响交互审计阅读。

### 6.2 展示方式

- 默认按会话和时间分页，不再无限追加全部事件。
- 支持按用户、会话、模型、日期和关键词筛选。
- 列表只显示摘要和必要元数据。
- 详情页分为 Prompt、Response、系统消息、工具调用和 Token 统计区域。
- 长文本使用折叠、复制和全文查看，不在列表中直接铺开。
- 空结果、加载中、解密失败和数据损坏都有明确状态。

### 6.3 流式和全文保存

- 服务端将 SSE 增量片段拼接成完整 Response 后再落库。
- Responses API 和 Chat Completions 使用统一的审计记录格式。
- 中途断流时保存已收到内容，并标记为 incomplete。
- 错误响应也保存错误类型和已收到的文本。
- 管理员点击详情后可以正常解密并查看全文。
- 修复“点击查看全文没有反应”、字段为空、前后端字段名不一致和长文本截断问题。
- 审计记录默认保留 1 个月，超过保留期自动清理。
- 管理员可以按筛选条件导出 Prompt/Response 审计记录。
- 审计列表增加分页和固定保留期，避免数据不断无界增长。

## 7. Skill 管理

- 管理端查看用户已安装 Skill、版本、来源和状态。
- 管理员向指定用户或全部用户下发 Skill。
- 客户端自动安装到标准 Skill 目录。
- 用户自行安装 Skill 后将名称、版本和状态回传服务端。
- 支持更新、禁用、卸载和失败重试。
- 管理端显示下发任务的成功、失败和待处理状态。

## 8. 用户和权限

- 用户可以使用用户名和密码注册。
- 新用户默认进入待审核状态。
- 管理员可以审核、拒绝、禁用和恢复用户。
- 未审核用户不能调用模型。
- 管理员、普通用户和审计查看权限保持清晰分离。
- 客户端登录失败时显示可读原因，不停留在无反馈状态。

## 9. 本地能力和 PowerShell

- PowerShell、终端和文件操作使用统一权限申请流程。
- 用户未授权时显示需要的具体权限和操作名称。
- 用户拒绝授权时显示原因，不静默失败。
- 普通权限、授权、拒绝、超时和执行错误均有独立提示。
- 管理员可配置默认权限策略。
- Windows 10 实机覆盖 PowerShell 调用、长命令、非零退出码和超时测试。

## 10. 客户端更新

- 服务端发布 Windows 安装包、版本号、更新说明、文件大小和 SHA-256。
- 客户端定时检查更新，也支持设置页手动检查。
- HTTP 模式下完成清单获取、下载、校验、安装和重启。
- 下载失败不影响当前版本继续运行。
- 新版本安装失败时保留旧版本。
- 管理端显示当前发布版本和已上传安装包。
- 提供发布包命名、目录结构和回滚说明。

## 12. 测试和验收标准

当前阶段以功能实现为主，不把完整测试作为功能完成的前置条件。先完成服务端、客户端、管理端和交付脚本的功能开发；功能完成后再集中执行本节中的测试和验收项目。开发过程中只保留必要的构建检查和明显错误修复。

### 12.1 服务端

- Ubuntu 24.04 干净环境可安装、启动、迁移和升级。
- `/healthz` 和 `/readyz` 正常。
- HTTP 登录、注册、审核、注销正常。
- PostgreSQL 重启后数据不丢失。

### 12.2 模型网关

- 每种目标供应商至少有一个模拟适配测试。
- Responses、Chat Completions、流式和非流式均通过。
- `/models` 自动发现通过。
- 429、401、超时和 5xx 能触发正确的 Key 切换。
- Token usage 能进入客户端、管理端和审计记录。

### 12.3 审计

- Prompt 和 Response 全文可查。
- 流式响应拼接完整。
- 系统事件不混入交互审计列表。
- 分页、筛选、详情、解密、全文查看和复制均可用。
- 长文本、断流和错误响应均有测试。

### 12.4 客户端

- Windows 10/11 安装、启动、登录和退出通过。
- 左侧栏在常见分辨率下无重叠和横向挤压。
- 新品牌 Logo 和文案在登录页、主界面、托盘、安装包和管理端一致。
- Token 用量显示正确，不出现付费金额文案。
- Skill、PowerShell、工作区、对话和设置功能通过点击级测试。
- HTTP 更新清单、下载、校验和安装通过。

## 13. 实施顺序

1. 建立需求基线和品牌素材规范。
2. 修复 HTTP-only 部署和更新链路。
3. 完成 Prompt/Response 审计重构。
4. 完成模型适配、自动发现和多 Key 轮询。
5. 完成客户端品牌、导航和 Token 用量界面。
6. 完成 Skill 下发、注册审核和 PowerShell 权限流程。
7. 完成部署脚本、安装包和全部说明文档。
8. 执行 Ubuntu、Windows、API、SSE、审计、更新和 UI 全量测试。
9. 生成最终内网交付包和验收报告。

## 14. 已确认事项

- 审计记录默认保留 1 个月，并允许管理员导出。
- 多 Key 采用全局轮询。
- 只支持 Windows 10/11 x64，不支持 Windows 32 位。
- Logo 由产品方直接生成并选定，交付时提供完整派生素材。
- 客户端服务端地址由首次启动填写并持久化。
- Windows 安装包不做代码签名。

## 15. 配置和密钥约束

真实 API Key 只能通过部署机上的环境变量或未提交的配置文件提供，不写入源代码、公开文档、测试夹具、安装包或 Git 历史。已经在聊天内容中暴露过的 Key 应先在供应商侧禁用并重新生成。
